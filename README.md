# Budget App

Python 표준 라이브러리만 사용하는 파일 기반 콘솔 가계부입니다. 거래 CRUD, 검색, 월별 요약, 예산, 카테고리 관리, CSV 가져오기·내보내기를 제공합니다. Python 3.10 이상이 필요합니다.

## 실행

```bash
python3 -m budget_app --help
python3 -m budget_app add
```

모든 명령은 `--help`를 지원합니다. 저장 폴더는 기본적으로 `./data`이며, `--data-dir 다른폴더`로 바꿀 수 있습니다. 최초 실행 시 `categories.jsonl`에 `food`, `transport`, `rent`, `salary`가 자동 생성됩니다.

## 명령어

```bash
python3 -m budget_app add
python3 -m budget_app list --limit 10
python3 -m budget_app search --from 2024-01-01 --to 2024-01-31 --type expense --tag meal
python3 -m budget_app summary --month 2024-01 --top 3
python3 -m budget_app budget set --month 2024-01 --amount 500000
python3 -m budget_app category add --name health
python3 -m budget_app category list
python3 -m budget_app category remove --name health
python3 -m budget_app update --id TX-ABC123 --amount 20000 --memo 수정
python3 -m budget_app delete --id TX-ABC123
python3 -m budget_app export --out export.csv --month 2024-01
python3 -m budget_app import --from import.csv
python3 -m budget_app recurring add --day 25 --type expense --category rent --amount 500000 --memo 월세
python3 -m budget_app recurring generate --month 2024-02
python3 -m budget_app backup
```

`add`는 기본적으로 날짜, 타입, 카테고리, 금액, 메모, 태그를 순서대로 대화형 입력받습니다. `update`는 옵션 방식으로 고정했으며 `--id`와 수정할 필드를 함께 입력합니다. 목록과 검색 결과는 최신순입니다. 사용 중인 카테고리는 삭제할 수 없습니다.

## 저장 형식

데이터는 JSONL로 네 파일에 나누어 저장합니다. JSONL은 한 줄에 하나의 JSON 값을 저장하는 형식이며, 이 프로젝트에서는 각 줄에 객체 하나를 기록합니다.

| 파일 | 내용 |
| --- | --- |
| `data/transactions.jsonl` | 거래의 `id`, `type`, `date`, `amount`, `category`, `memo`, `tags` |
| `data/categories.jsonl` | 카테고리의 `name` |
| `data/budgets.jsonl` | 월별 `month`, `amount` 예산 |
| `data/recurring.jsonl` | 반복 내역의 `id`, `day`, `type`, `amount`, `category`, `memo`, `tags` |

수정·삭제·카테고리 변경·예산 변경은 임시 파일에 기록한 뒤 원자적으로 교체하여 중간 상태가 남을 가능성을 줄입니다. 거래 수정·삭제도 JSONL 전체를 리스트로 로드하지 않고 한 행씩 임시 파일에 재작성합니다. 거래 추가는 기존 행과 새 행을 임시 파일에 순차 기록한 뒤 원자적으로 교체합니다. CSV import는 현재 파일의 복사본에 먼저 전체 내용을 반영하고, 모든 행의 검증이 성공한 경우에만 원본과 원자적으로 교체합니다. 하나라도 오류가 있으면 staging 파일을 폐기하고 기존 거래 파일은 변경하지 않습니다.

### 스트리밍 오류와 원자성 정책

JSONL을 스트리밍으로 읽을 때 공백 행은 건너뛰지만, JSON 파싱 오류나 필드·값 검증 오류가 발생하면 해당 명령을 즉시 중단합니다. 오류가 난 행만 조용히 건너뛰어 뒤의 데이터를 계속 처리하지 않습니다. 서비스 예외는 로그에 남고 CLI는 `[오류]`와 `[힌트]`를 출력하며 종료 코드 1을 반환합니다.

파일을 변경하는 작업은 성공한 전체 결과만 원본에 반영하는 것을 원칙으로 합니다. 거래·반복 내역 추가, 수정·삭제, 카테고리·예산 변경, CSV 가져오기, CSV 내보내기는 임시 파일을 만든 뒤 마지막에 원자적으로 교체합니다. 처리 중 오류가 나면 임시 파일을 삭제하고 기존 파일(또는 기존 CSV)을 그대로 둡니다. 따라서 CSV 가져오기는 한 행이라도 실패하면 전체 행이 반영되지 않으며, 내보내기도 기존 출력 파일을 덮어쓰지 않습니다. 반복 내역 일괄 생성 역시 모든 생성 대상이 준비된 뒤 한 번에 교체됩니다.

원자적 교체는 한 프로세스 안에서 파일이 중간 상태로 보이는 것을 줄이는 저장 방식입니다. 동시 실행 중인 여러 프로세스의 충돌 조정이나 백업을 대신하지는 않으며, 디스크·권한 오류가 발생하면 명령은 중단되고 오류를 반환합니다.

### JSONL과 CSV의 장단점

JSONL과 CSV 모두 한 레코드씩 스트리밍으로 읽으면 전체 파일을 메모리에 올리지 않고 처리할 수 있습니다. 실제 메모리 사용량은 파서와 레코드 표현에 따라 달라지지만, 메모리 절약은 형식 자체보다 처리 방식에 달려 있으며 JSONL만의 장점은 아닙니다.

| 관점 | JSONL | CSV |
| --- | --- | --- |
| 대용량 | 한 줄씩 읽고 추가하기 쉽습니다. 다만 매 레코드에 필드 이름을 반복하므로 같은 표 데이터라면 파일이 더 커질 수 있습니다. | 행 단위 순차 처리와 추가가 가능하며, 헤더를 한 번만 저장해 보통 더 작습니다. 필드 안에 줄바꿈이 있으면 단순한 줄 단위 분할 대신 CSV 파서가 필요합니다. |
| 호환성 | JSON을 다루는 프로그램과 연동하기 좋습니다. 파일 전체가 하나의 JSON 문서는 아니므로 줄별 파싱이나 JSONL 지원이 필요합니다. | Excel·스프레드시트·분석 도구에서 널리 지원합니다. 인코딩·구분자·자료형 해석 차이에 주의해야 합니다. |
| 편의성·데이터 표현 | 숫자·배열·`null`을 그대로 표현하고 객체와 변환하기 쉽습니다. 사람이 표처럼 비교하거나 수정하기에는 번거롭습니다. | 고정된 열의 데이터를 사람이 표로 확인하고 수정하기 편합니다. 배열과 결측값 표현, 숫자 변환에는 별도 규칙이 필요합니다. |

### 이 프로젝트에서 JSONL을 선택한 이유

- **거래 구조 보존:** `amount`는 정수, `tags`는 배열, `recurring_id`는 문자열 또는 `null`로 저장합니다. 특히 태그 배열을 직접 저장할 수 있어, CSV 입출력에서 사용하는 쉼표 구분 문자열로 변환할 필요가 없습니다.
- **객체 변환의 편의성:** 거래를 딕셔너리로 변환한 뒤 Python 표준 `json` 모듈로 저장하고 복원합니다. CSV도 표준 라이브러리로 처리할 수 있지만, JSONL은 배열과 `null`을 표현하기 위한 별도 문자열 규칙이 덜 필요합니다. 카테고리·예산·반복 내역도 같은 읽기 방식을 공유합니다.
- **외부 교환에는 CSV 사용:** 내부 저장은 자료형과 구조를 보존하는 JSONL로 하고, 사용자가 Excel 등에서 활용할 수 있도록 CSV 가져오기·내보내기 기능을 둡니다.

JSONL 선택의 핵심은 자료형·배열 보존과 객체 변환의 편의성입니다. CSV도 스트리밍과 끝에 추가가 가능하므로, 대용량이라는 이유만으로 JSONL이 더 빠르거나 메모리를 덜 쓰는 것은 아닙니다.

### 현재 구현의 메모리 처리와 한계

`_read_jsonl()`과 `TransactionRepository.stream()`은 제너레이터로 한 건씩 읽습니다. 거래 수정·삭제도 전체 리스트를 만들지 않고 임시 파일에 순차 기록합니다. 이는 현재 구현의 메모리 절약 방식이며, CSV에서도 `csv.DictReader`로 같은 방식의 순차 처리가 가능합니다.

현재 검색·집계는 전체 거래를 읽고 수정·삭제는 전체 파일을 재작성하며, 거래 추가도 중복 ID 확인을 위해 전체를 읽습니다. 원자적 교체는 저장소 구현이 제공하는 보호이며 JSONL 자체의 기능은 아닙니다. 조회 속도·동시 쓰기·트랜잭션이 중요해지면 아래 대체 저장소 선택지를 검토해야 합니다.

## CSV 스키마

`export`와 `import`는 UTF-8 BOM, 헤더 포함 형식을 사용합니다. `export`는 `--month YYYY-MM` 또는 `--from YYYY-MM-DD`/`--to YYYY-MM-DD` 조건을 하나 이상 요구합니다.

BOM(Byte Order Mark)은 파일 맨 앞에 추가되는 특수한 바이트 표시입니다. 이 프로그램은 CSV를 `UTF-8-sig` 인코딩으로 저장하여 BOM을 포함합니다. Excel이 이 표시를 보고 파일을 UTF-8로 인식하므로, CSV를 Excel에서 열 때 한글이 깨지는 문제를 줄일 수 있습니다. 일반 UTF-8 파일과 데이터 내용은 같고 파일 시작 부분에 표시가 하나 추가된 형태입니다.

| column | 필수 | 설명 |
| --- | --- | --- |
| `id` | 아니오 | 없으면 import 시 자동 생성 |
| `date` | 예 | `YYYY-MM-DD` |
| `type` | 예 | `income` 또는 `expense` |
| `category` | 예 | 등록된 카테고리 |
| `amount` | 예 | 0보다 큰 정수 |
| `memo` | 아니오 | 문자열 |
| `tags` | 아니오 | 쉼표로 구분한 문자열 |

예시:

```csv
id,date,type,category,amount,memo,tags
TX-001,2024-01-15,expense,food,15000,점심,"meal,weekday"
TX-002,2024-01-25,income,salary,3000000,월급,
```

## 구조와 학습 포인트

| 계층 | 파일 | 책임 |
| --- | --- | --- |
| 모델 | `models.py` | `Transaction` 데이터 구조와 날짜·타입·금액 기본 검증 |
| 저장소 | `repositories.py` | 거래·카테고리·예산 JSONL의 스트리밍 읽기와 안전한 파일 쓰기 |
| 서비스 | `service.py` | CRUD, 검색, 요약, 예산, CSV 업무 규칙 |
| CLI | `cli.py` | 명령행 옵션·대화형 입력·출력·종료 코드 |

CLI는 입력을 해석하고 서비스에 요청하며, 서비스는 저장소를 통해 데이터를 다룹니다. 이 분리 덕분에 화면 출력 방식을 바꾸어도 거래 검증과 계산 규칙을 함께 수정할 필요가 없습니다. `Transaction`, `TransactionRepository`, `CategoryRepository`, `BudgetRepository`, `BudgetService`처럼 여러 클래스로 책임을 나누고 함수마다 타입 힌트를 적용했습니다.

`Transaction`은 `@dataclass(frozen=True)`로 정의했습니다. `frozen=True`는 객체를 생성한 뒤 필드 값을 바꿀 수 없게 합니다. 따라서 저장된 거래의 날짜·금액·카테고리가 실수로 변경되는 일을 줄일 수 있습니다.

```python
transaction = Transaction("TX-001", "expense", "2024-01-15", 15000, "food")
transaction.amount = 20000  # FrozenInstanceError 발생
```

거래를 변경해야 할 때는 기존 객체를 직접 수정하지 않고 새로운 `Transaction` 객체를 생성합니다. 또한 `tags`를 변경 가능한 `list` 대신 `tuple`로 저장해 태그 내부 내용도 함부로 바뀌지 않도록 했습니다. `frozen=True`는 객체 내부의 리스트나 딕셔너리까지 자동으로 불변으로 만들지는 않기 때문에, 컬렉션 필드의 자료형도 함께 선택해야 합니다.

`TransactionRepository.stream()`과 JSONL 읽기 함수는 `yield` 기반 제너레이터입니다. 반복할 때 한 행씩 `Transaction`을 생성하므로 대용량 파일도 전체 내용을 리스트로 만든 뒤 처리하지 않아 메모리 사용량을 줄일 수 있습니다. 수정·삭제도 같은 방식으로 한 행씩 읽어 임시 파일에 기록합니다. 최신순 정렬이 필요한 목록·검색은 최대 1,024개씩 정렬한 임시 청크 파일을 만든 뒤 병합하므로, 전체 거래를 메모리에 올리지 않고 순서를 유지합니다.

`service.py`의 `@logged_timed` 데코레이터는 서비스 함수의 예외 로그와 실행 시간 측정을 공통 처리합니다. 핵심 업무 함수마다 로그 코드를 복사하지 않아도 되고, CLI는 사용자에게 원인과 힌트를 출력하는 역할에 집중할 수 있습니다.

타입 힌트는 함수의 입출력 계약을 코드에 기록합니다. 예를 들어 다음 선언은 `Transaction` 목록과 선택적 정수 제한을 받아 카테고리·금액 튜플 목록을 반환한다는 뜻을 IDE와 정적 검사 도구에 전달합니다.

```python
def summary(
    self, month: str
) -> tuple[int, int, list[tuple[str, int]]]:
    ...
```

실제 서비스의 `stream() -> Iterator[Transaction]`, `summary() -> tuple[int, int, list[tuple[str, int]]]` 같은 선언도 함수 사이의 데이터 계약을 명확하게 하여 자동 완성, 코드 리뷰, 변경 영향 확인에 도움을 줍니다.

오류는 스택트레이스 대신 `[오류]` 원인과 `[힌트]` 해결 방향으로 출력되며, 정상 종료는 0, 오류 종료는 1을 반환합니다.

## 보너스 기능

`backup`은 `data/backup-YYYYMMDD-HHMMSS/` 디렉터리를 만들고 현재 JSONL 저장 파일을 복사합니다. 백업 시점의 데이터를 별도로 보존할 수 있습니다.

`recurring add`로 매월 반복할 거래 템플릿을 저장하고, `recurring generate --month YYYY-MM`으로 해당 월의 거래를 생성합니다. 31일처럼 해당 월에 없는 날짜는 그 달의 마지막 날로 보정하며, 같은 반복 내역을 같은 월에 다시 생성해도 중복 거래를 만들지 않습니다.

목록과 검색은 고정 폭 열을 사용해 표 형태로 출력합니다. 거래를 전체 리스트로 만들지 않고 한 행씩 출력하므로 `--limit`을 사용할 때도 스트리밍 처리를 유지합니다.

## 대용량(100k) 대응 방안

### 현재 구현의 100k 기준 특성
| 기능 | 현재 처리 방식 | 100k에서 예상되는 병목 |
| --- | --- | --- | --- |
| `list`/`search` | 전체 파일 스트리밍 → 일치 행을 1,024건씩 임시 청크로 정렬 → 최신순 병합 | 필터 결과가 많으면 디스크 I/O와 임시 파일 생성 |
| `summary` | 전체 거래를 한 번씩 순회하며 해당 월만 집계 | 매 실행마다 전체 파일을 읽음 |
| `add` | 중복 ID 확인 후 기존 행과 새 행을 임시 파일에 순차 기록해 원자적으로 교체 | 추가 1건마다 O(n) 읽기·쓰기 |
| `update`/`delete` | 전체 파일을 한 번 읽어 임시 파일에 재작성 | 100k 전체 재작성 시간과 디스크 여유 공간 |
| CSV `import` | 행마다 `add`를 호출 | 중복 ID 검사 때문에 대량 import가 최악의 경우 O(n²) |
| `backup` | JSONL 파일을 그대로 복사 | 파일 크기에 비례하는 I/O |

### 대체 저장소 선택지

| 선택지 | 적합한 상황 | 장점 | 고려 사항 |
| --- | --- | --- | --- |
| SQLite | 한 컴퓨터의 단일 사용자, 100k~수백만 건, 설치 부담 최소화 | Python 표준 라이브러리(`sqlite3`)로 사용 가능, 트랜잭션·인덱스·집계·중복 방지 지원 | 쓰기 동시성은 제한적이며 DB 파일 백업/잠금 정책 필요 |
| PostgreSQL/MySQL | 여러 사용자/프로세스, 지속적인 쓰기, 서비스 배포 | MVCC, 강한 제약조건, 동시성, 인덱스·집계·운영 도구 | 별도 서버·권한·백업·마이그레이션 운영 필요 |

### SQLite로 마이그레이션하는 절차

단일 컴퓨터에서 사용하는 현재 구조라면 SQLite를 우선 권장합니다. Python 표준 라이브러리의 `sqlite3`만으로 구현할 수 있고, 기존 CLI·서비스 계층은 유지한 채 저장소 계층만 교체할 수 있습니다.

1. **마이그레이션을 준비합니다.** 쓰기 작업을 중지하고 `python3 -m budget_app backup`으로 현재 JSONL 네 파일을 백업합니다. 백업 디렉터리와 SQLite DB의 경로를 별도로 정하고, 실패 시 JSONL 저장소로 되돌릴 수 있도록 기존 파일을 보존합니다.
2. **SQLite 스키마를 만듭니다.** `transactions` 테이블에 거래 필드를 만들고 `id`를 `PRIMARY KEY`로 지정합니다. `categories.name`에는 `UNIQUE`, `budgets.month`와 반복 내역의 `id`에도 필요한 고유 제약을 둡니다. `date`, `type`, `category`에는 검색 목적의 인덱스를 만들고 `tags`는 현재 JSON 배열을 JSON 문자열로 저장하거나 별도 `transaction_tags` 테이블로 정규화합니다.
3. **전용 저장소 구현을 추가합니다.** 기존 `TransactionRepository`와 같은 `stream`, `append`, `rewrite` 계약을 `SQLiteTransactionRepository`로 구현합니다. 서비스와 CLI가 구체적인 파일 형식을 직접 알지 않도록 생성 시 저장소를 주입하는 방식은 유지합니다.
4. **검증된 일괄 변환기를 실행합니다.** JSONL을 한 행씩 읽어 SQLite의 단일 트랜잭션 안에서 `executemany` 또는 prepared statement로 삽입합니다. 각 파일의 행 수, 거래 ID의 유일성, 금액 합계, 월별 수입·지출 합계, 카테고리·태그를 이전 전후로 비교하고 검증이 실패하면 `ROLLBACK`합니다.
5. **읽기 결과를 비교합니다.** 동일한 데이터에 대해 `list`, `search`, `summary`, CSV `export`를 양쪽 저장소에서 실행하고 결과를 비교합니다. 최신순 정렬, 날짜 범위, 태그, `null` 값, UTF-8 한글이 일치하는지 확인합니다.
6. **저장소를 전환합니다.** 검증이 끝난 뒤 기본 저장소를 SQLite로 바꾸고, 첫 실행 시 `PRAGMA foreign_keys = ON`과 적절한 busy timeout을 설정합니다. 전환 시점과 스키마 버전을 기록하고, 운영 중에는 정기적으로 SQLite 백업을 생성합니다.
7. **롤백 기준과 기간을 둡니다.** 전환 후 일정 기간 JSONL 원본을 삭제하지 않습니다. 데이터 불일치, 잠금 오류, 성능 저하가 발생하면 쓰기를 중지하고 SQLite의 마지막 정상 백업을 보존한 뒤 JSONL 저장소로 설정을 되돌립니다. 문제가 없음을 확인한 후에만 오래된 JSONL을 보관 정책에 따라 정리합니다.

PostgreSQL/MySQL로 이전할 때도 1~5단계의 데이터 검증 절차는 동일합니다. 다만 3단계에서 연결 풀·마이그레이션 도구·권한을 추가하고, 6단계에서 DB 접속 정보와 네트워크 장애·동시성 정책을 운영 환경에 맞게 설정해야 합니다.

### 마이그레이션 후 예상 성능 개선

아래 수치는 **100,000건, 로컬 SSD, 단일 프로세스, SQLite 인덱스(`date`, `type`, `category`)와 일괄 트랜잭션을 적용한 경우의 목표 범위**입니다. 실제 개선 폭은 파일 크기, 디스크, 검색 선택도, Python 버전과 동시 실행 여부에 따라 달라지므로 전환 전후 동일 조건의 벤치마크로 확인해야 합니다.

| 기능 | 현재 JSONL의 비용 | SQLite 전환 후 기대 변화 | 예상 개선치 |
| --- | --- | --- | --- |
| `list`/`search` | 전체 파일 스캔 및 결과 정렬, `O(n)` | 인덱스 검색 후 필요한 행만 조회, 대체로 `O(log n + k)` | 약 2~10배 빠름 |
| `summary` | 매번 전체 거래 스캔, `O(n)` | 날짜 인덱스와 SQL 집계 사용 | 약 5~20배 빠름 |
| `add` | 중복 확인과 전체 파일 재작성, `O(n)` | PK 중복 검사와 한 행 삽입 | 약 10~100배 빠름 |
| `update`/`delete` | 전체 파일 재작성, `O(n)` | PK로 대상 행을 찾아 갱신·삭제 | 약 10~100배 빠름 |
| CSV `import` | 행마다 중복 검사·재작성되어 최악 `O(n²)` | 단일 트랜잭션의 batch insert, `O(n)` | 약 20~200배 빠름 |
| 메모리 사용 | 스트리밍으로 낮지만 임시 정렬 파일 사용 | 인덱스와 페이지 캐시 사용, 전체 재작성 불필요 | 대량 수정·가져오기에서 임시 디스크와 메모리 부담 감소 |

성능 비교는 다음 항목을 고정해 측정합니다: 동일한 100k 데이터셋, 동일한 검색 조건, 캐시 워밍 여부, CSV 파일 크기, 측정 횟수와 중앙값. 기능별로 `time.perf_counter()`를 사용해 5회 이상 반복하고, 첫 실행과 캐시가 따뜻한 실행을 구분해 기록합니다. SQLite가 제공하는 조회·집계·쓰기 이점은 인덱스와 트랜잭션을 올바르게 적용했을 때의 기대치이며, 네트워크 DB로 바꾸는 경우에는 네트워크 왕복 시간과 연결 풀 설정까지 별도로 측정해야 합니다.
